# VOID RUNNER 3.0 — "Technicolor Void" revamp: audit + design

**Date:** 2026-09-27 · **Branch:** `claude/game-revamp-dos-aesthetic-vdk6fy`

**Ask:** revamp the whole game so it looks and plays like the vivid mid-90s DOS tunnel-shooters it is
an homage to: saturated 256-color textures, pre-rendered-looking 3D sprites, and fun on a PC. That
means auditing the available Godot tooling, deciding what can be built, and then building it in order.

---

## 1. Audit

### 1.1 Skills and plugins available to this session

| Source | Godot-relevant? | Verdict |
|---|---|---|
| Enabled skills (docs, pdf/docx/pptx/xlsx, browser/computer-use, deep-research, skill-creator, …) | No | None are about Godot, GDScript, shaders or game art. |

That breaks hard rule #1 (everything shipped is generated by code in this repo, no imported assets), and AI-generated art from a hosted model can't be shown to be clean of third-party material. |
| Plugin catalog: **Unity** | No | Wrong engine. |
| Earlier M7 plan: Blender-via-MCP baked spritesheets | Partly | Not available in this environment. It would also have needed the M0.1 rule change, where committed PNGs become shippable. The approach below gets the same "pre-rendered 3D" look **without** any rule change. |

**Conclusion:** no skill or plugin does anything this repo's constraints allow that Claude can't do
directly. The useful capability is **Claude + a real Godot 4.7 binary**. This container can run:

- `godot --headless` for the smoke/perf tests (script and simulation correctness), and
- `xvfb-run godot --rendering-driver opengl3` (Mesa llvmpipe, the real GL Compatibility renderer) for
  **rendered screenshots**. So every visual change here is checked by looking at real frames, not
  just by reasoning about code.

### 1.2 What the 2.2 build looked like (baseline captures, same probe)

- **Tunnels read as near-black.** The wall base color was `#1f242e`. Per-vertex lighting on 12 m
  quads, a 40-color palette weighted to dark greys, and fog starting at 10 u quantized most of the
  frame to 3–4 near-black entries.
- **Sprites were tiny flat pixel drawings.** They were 32 px hand-plotted ellipses and rects, so
  they couldn't carry the metallic, pre-rendered 3D look of the era.
- **The one boss model was tinted three ways.** Every boss used the same art.
- **All text used Godot's default anti-aliased UI font.** This was the single most un-DOS thing on
  screen.
- **Lighting came from real `OmniLight3D`s.** That's the most expensive path on the single-threaded
  WebGL build, and it doesn't produce the banded "sector light" look of 1995 software renderers.

### 1.3 What Claude can build in Godot 4.7 GL Compatibility (verified by prototype)

Every row was prototyped in a scratch project and rendered under the real Compatibility renderer
before any game code changed.

| Technique | How | Status |
|---|---|---|
| **Pre-rendered 3D sprites, baked at boot** | Enemies and bosses are *code-built* models (Godot primitive meshes plus one custom "studio" shader). They're rendered by an orthographic camera into one atlas SubViewport per sprite class (8 yaw angles × 2 anim frames) and read back once. Hit-flash frames are derived with native `Image` ops. | ✅ prototyped |
| **Sector lighting shader** | A custom unshaded spatial shader: baked per-vertex sector light, dynamic point lights passed as uniform arrays (headlight, muzzle, explosions, glowing shots), full-bright texels flagged by texture alpha, and light quantized into bands. | ✅ prototyped |
| **256-color VGA palette + fast quantizer** | 16 hue ramps × 16 shades. A 512×512 lookup table is built **once on the GPU**, so the per-frame dither is one `texelFetch` instead of a 256-iteration loop per pixel. | ✅ prototyped |
| Procedural pixel textures | `FastNoiseLite` seamless noise (native) is mapped into palette ramps, then bevels, rivets, grilles, light panels and hazard stripes are painted on top. Mipmapped nearest filtering keeps close-ups chunky and distance shimmer-free. | design |
| Bitmap pixel font | An original 6×9 glyph set authored in code and packed into a `FontFile` atlas. It becomes the global UI font. | design |
| CRT / scanline filter | A screen-reading canvas shader as a top layer (optional setting). | design |

## 2. Design pillars for 3.0

1. **Vivid, not murky.** Keep the chunky look: 320×200, nearest filtering, palette-quantized
   output. But light the world like the era's best-looking games did: colored lamps you can see,
   glowing panels, bright arenas, and darkness used as punctuation instead of as the default.
2. **Everything is still code.** No imported assets and no rule change. The sprite forge,
   textures, font and audio are all generated at runtime from this repo.
3. **The WebGL build stays smooth.** No `OmniLight3D`s at all (dynamic light moves into one shader).
   The sprite atlases bake behind the loading overlay. Every new material registers in the warm-up
   rig. The pooling and dirty-draw rules from 2.2 still apply.
4. **Readable combat.** Each enemy has a distinct silhouette, color and behavior. Shots glow and
   light up the walls. Explosions are big.
5. **The tests keep passing.** The smoke test stays the regression net. New systems add asserts.

## 3. Phased plan (each phase: implement → smoke test → rendered capture review → commit)

| Phase | Scope |
|---|---|
| 1 | 256-color palette (`palette.gd`) and GPU LUT quantizer (`palette_lut.gd`, `palette_lut.gdshader`, dither shader rewrite). Amber mode kept. |
| 2 | `sector.gdshader` plus `LightRig`, which replaces every `OmniLight3D`. Chamfered octagonal tunnel cross-section (with collision support), baked lamp lighting, and a new texture painter with per-theme variants. Split bulkhead doors and a vortex exit portal. |
| 3 | `SpriteForge`: GPU-baked atlases for every enemy (plus 3 new ones), three distinct boss models, and pickups. Directional (8-angle) sprite selection, noise-fireball explosions, and additive glowing projectiles with trails. |
| 4 | Pixel font everywhere, a textured cockpit console with LED gauges, DOS-window menus, a title logo with an attract-mode flythrough behind the start screen, and an optional CRT filter. |
| 5 | Timed power-ups (OVERDRIVE, PHASE SHIELD, POWER CORE). New enemies: STINGER (telegraphed dive), SPINNER (radial bursts) and floating MINES. A distinct attack identity per boss. |
| 6 | Audio polish: FM-flavored instruments and punchier SFX (budget permitting). |
| 7 | Verification (smoke, rendered probe, perf probe, GLES3 driver pass, web export), docs, push. |

## 4. Risks and how they're handled

- **Headless tests have no renderer.** In a headless run the sprite forge detects the dummy
  renderer and falls back to the existing `SpriteGen` pixel sprites. Frame-array shapes are
  identical, so every smoke assertion still exercises the real code paths.
- **WebGL uniform limits.** The palette is passed as a 256×1 texture, not a 256-entry uniform array
  (a minimal WebGL2 guarantees only 224 fragment uniform vectors). There are 8 dynamic lights.
- **First-use shader stalls on web.** One sector shader covers all world geometry. Sprites use two
  material variants and FX use one additive variant. All of them are exercised in the warm-up rig.
- **Collision vs. new geometry.** The chamfers cut corners, so `PathGen.clamp_to_ring` and the
  player's wall collision both gain the diagonal plane test. The smoke test asserts no position can
  sit outside the octagon.
